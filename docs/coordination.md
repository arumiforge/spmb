# Coordination of parallel sessions

How several Claude sessions build one phase at the same time without stepping on
each other. First used for phase 2 (registration), again for phase 3 (placement test); reuse it for later phases.
The repository is the only shared memory (see `.claude/skills/spmb-session`).

## Roles

| Role | Who | May touch |
| --- | --- | --- |
| Coordinator | One session (`spmb:coordinator`) | The integration branch, shared files, shared docs, merges into the integration branch |
| Worker | One session per work package (`spmb:worker`) | Only the files its package owns (listed in the phase plan, e.g. `docs/phase-3-plan.md`) |
| User (Arumi Studios) | Human | Merges the integration branch into `main`; answers open questions |

## Protocol

1. **Integration branch** `phase-N` is created from `origin/main`. Only the
   coordinator commits to it (merges of reviewed PRs and conflict fixes).
2. **Foundation first, alone.** Before any worker starts, the coordinator lands
   everything shared in one PR into `phase-N`: module folders and `Config/Module.php`,
   all migrations for shared tables (non-overlapping timestamps), shared models,
   permission keys in `Config\AuthGroups` (+ `AuthGroupsTest`), settings defaults,
   menu entries, shared language keys, audit labels and the phase plan
   (work packages, owner session, files each one may touch, interfaces).
3. **Workers** branch from `phase-N` (`feat/pN-<package>`), commit only their own
   files and open one PR into `phase-N`. A worker that needs a change in a shared or
   another package's file does not make it: it asks the coordinator (message to the
   coordinator session, or a "Needs from coordinator" section in the PR description).
4. Workers **never edit** `docs/progress.md`, `docs/decisions.md`, `CHANGELOG.md`,
   `docs/requirements.md`, `docs/roadmap.md` or `docs/architecture.md`. They put
   proposed decisions, changelog lines, requirement status and progress notes in
   their PR description; the coordinator merges them into the shared docs.
   A worker may write its own module page `docs/modules/<module>.md`.
5. **Review and merge**: the coordinator reads the diff, merges the PR locally onto
   the current `phase-N`, runs `composer test`, `composer lint` and `npm run build`,
   checks the screenshots, asks for fixes by message, and merges into `phase-N`
   when CI is green and the PR fits the plan. Conflicts on `phase-N` are resolved by
   the coordinator. Workers rebase or merge `phase-N` into their branch when asked.
6. **Phase PR**: when all packages are in, the coordinator opens one PR
   `phase-N` → `main` with the summary, updated docs and open questions.
   **The user merges `main`**; no session merges into `main`.
7. Finished workers are archived by the coordinator.

## Notes from the platform round (2026-11-22)

- The integration branch can also be the coordinator session's own branch (it was
  `pw/zealous-albattani-2rz2z1`, see `docs/platform-plan.md`); workers branch from it and open PRs into it.
- Workers are started as separate cloud sessions on the same environment. That environment must run the
  repository's setup script (`docs/cloud-environment.md`); a setup script that fails stops every worker
  before it starts.
- After each worker merge: run the full suite, `composer lint`, `npm run build`, look at the changed pages at
  360 and 1280 px, archive the worker, and tell the remaining workers to merge the integration branch when
  shared files changed.
- Tools may add a "Generated by …" footer to PR descriptions; remove it with the GitHub tool (editing through
  `gh api` may add it back).

## Rules for every session

- Start with `spmb-session`; git identity `Arumi Studios <arumiforge@gmail.com>`,
  `git config core.hooksPath .githooks`.
- Conventional Commits in English; Arumi Studios is the only author and committer;
  no AI attribution of any kind in commits, PR bodies or comments. If a tool appends
  a "Generated by …" footer to a PR body or comment, edit it out.
- Docs in English; UI in friendly Indonesian (`spmb-copy`); Indonesian URL slugs;
  breadcrumbs on every admin page; responsive 360 → 1920 px; `npm run build` after
  adding Tailwind classes.
- Every route has a permission test (allowed role, denied role, guest).
- Playwright screenshots at 360 and 1280 px of every new page, checked before the PR.
- New dependencies only MIT/BSD/Apache-2.0/ISC, listed in `THIRD_PARTY_NOTICES.md`,
  and added by the coordinator (one `composer.lock`); ask the user for anything else.
- Personal data (UU PDP): minimum fields, uploads outside `public/`, served through
  authorised controllers, QR carries a random token, every change to applicant data
  goes through an audited model.
- Push often: a cloud container can be reclaimed at any time.
