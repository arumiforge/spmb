# Instructions for Codex: make the SPMB visual assets

You are making the visual assets for **SPMB**, a white-label school admission web app for Indonesian
junior high schools, built by Arumi Studios. The first school is SMP NU Al Ma'ruf Kudus, but every asset
you make must suit any school.

**Your job: make the assets the briefs ask for and deliver them in one pull request per batch.**
Claude (the developer agent of this repository) writes the briefs, reviews your pull request and wires
the assets into the app. You do not touch application code.

## 1. Scope (strict)

- You may add or change files **only inside `ai/generated/`**, plus the `status:` line in the front
  matter of the briefs you delivered and the Status column of the queue in `ai/README.md`.
- Never change `app/`, `public/`, `resources/`, `docs/`, other briefs, or anything outside `ai/`.
- Never copy school logos or the content of `flowbite/` (licensed source) into an asset.
- Work on a new branch `art/codex-<YYYYMMDD>-<batch>` (for example `art/codex-20261123-svg-kit`),
  created from the latest `main`. Open **one pull request into `main`** per batch. **Never merge it.**

## 2. Git identity and commit rules

The repository accepts commits from one author only, and CI checks it (`.github/workflows/commit-policy.yml`).

```bash
git config user.name "Arumi Studios"
git config user.email "arumiforge@gmail.com"
git config core.hooksPath .githooks
```

- Conventional Commits in English, for example `feat(ai): add pattern and divider kit (015, 016)`.
- **No AI attribution anywhere**: no `Co-authored-by`, no "Generated by Codex/ChatGPT/OpenAI", no tool
  footers or links in commits, the pull request title, body or comments. Remove any footer a tool adds.
- Push after each finished brief, so nothing is lost.

## 3. Read first, in this order

1. [`style-guide.md`](style-guide.md) — identity, respect rules for religious elements, palette, cast,
   painting look, SVG rules, D-070 visual rules. **Mandatory for every asset.**
2. [`README.md`](README.md) — the queue. Make only rows with status `requested`, batch by batch, in ID order.
3. Each brief `prompts/<ID>-<name>.md` — purpose, where it is used, composition, files, alt text and
   acceptance checks. The brief wins over this page when they differ; the style guide's section 2
   (respect) always wins.

## 4. Where files go

Everything you deliver lives under `ai/generated/`:

```
ai/generated/
├── <name>[-variant].webp          painting masters at the generator's native size, WebP quality 92
├── install/                       files ready to install, already at their final size
│   ├── img/<area>/<file>          → copied by Claude to public/assets/img/<area>/<file>
│   └── css/<file>.css             → copied by Claude to resources/css/visual/<file>.css
├── demo/index.html                one static preview page for every SVG/CSS asset (see section 6)
└── README.md                      the delivery table (update it in every pull request)
```

- Existing PNG originals in `ai/generated/` (IDs 001–012) stay where they are; never delete them.
- File names are lowercase Indonesian kebab-case, exactly as the brief says. Variants use the suffixes
  `-dark`, `-hijau` and `-dark-hijau` (style guide → Variants).
- `ai/output/` is a git-ignored scratch folder: put drafts and your check screenshots there.

## 5. Paintings (WebP)

1. Generate with your image generation tool (or the OpenAI Images API with a `gpt-image` model, if your
   environment provides a key) in the shape the brief names: square 1024×1024, landscape 1536×1024 or
   portrait 1024×1536, with transparent or white background as stated. Use the brief's **Prompt** exactly;
   the Composition and Avoid sections are part of the brief.
2. **Look at every result** and check it against the brief and the style guide before you accept it.
   Regenerate (at most three times) with a short correction when a check fails. Typical failures: text or
   letter-like marks, Arabic-looking script, a logo-like emblem, a drawn checkerboard instead of alpha,
   a busy empty area, realistic or 3D faces, more than one accent colour.
3. Make the variants by **editing the accepted light image**, not by generating a new scene: dark
   (style guide §8), green accent (§9), and dark green accent (apply §9 to the dark image).
4. Export:
   - master: `ai/generated/<name>[-variant].webp`, native size, quality 92, alpha kept;
   - installed file: `ai/generated/install/img/<area>/<name>[-variant].webp`, resized to the width in the
     style guide's size table (Lanczos), quality 80–85, within the budget, alpha kept.
   Pillow example: `img.resize((w, round(img.height * w / img.width)), Image.LANCZOS).save(path, 'WEBP', quality=82, method=6)`.
5. If you cannot generate images in your environment, deliver the SVG/CSS batch only and say in the
   pull request which painting briefs are blocked and why. Never substitute stock photos, clip-art or
   another style.

## 6. SVG and CSS assets

1. Write the SVG by hand, following style guide §5 (masks are `#000` on transparency; inline SVGs use
   `currentColor`; no text, scripts, images or external references; within the size budget).
2. CSS files are plain CSS (no build step needed, no `@apply`), wrapped in `@layer components { … }`,
   using only the app's tokens: `var(--color-primary-50 … 950)` and `var(--brand)`, Tailwind's grey
   scale values written as hex, and `.dark` (class on `<html>`) for dark mode. Include
   `-webkit-mask-*` next to `mask-*`. Every animation and transition sits inside
   `@media (prefers-reduced-motion: no-preference)` or is switched off under `reduce`.
   Support Windows high contrast with `@media (forced-colors: active)` where the brief asks.
3. Build or extend `ai/generated/demo/index.html`: a single static page (no CDN, no external fonts) that
   links the CSS from `../install/css/`, defines the primary tokens the same way as
   `resources/css/app.css` (copy the `color-mix()` scale), and has two switches: brand colour
   (blue `#2563EB` / green `#005C2F`) and light/dark (toggle `.dark` on `<html>`). Show every asset of the
   batch in all its states (hover/focus/disabled for buttons; patterns at the opacity the CSS sets;
   dividers between two coloured sections; the loader animating and with reduced motion).
4. Check the demo with Playwright (preinstalled in many environments) at 360×800 and 1280×800, light and
   dark, blue and green, plus one run with `reducedMotion: 'reduce'`. Save screenshots in `ai/output/`
   and look at them. Nothing may overflow horizontally at 360 px.

## 7. Check before you open the pull request

Run the checker from the repository root:

```bash
python3 ai/tools/check_assets.py            # every brief with status generated
python3 ai/tools/check_assets.py 015 016    # only these briefs
```

It checks file names, sizes, budgets, alpha, SVG safety rules and the D-070 CSS rules. Fix every `FAIL`.
Then do the brief's own **Acceptance checks** by eye and tick them in the pull request body.

## 8. Deliver

1. Set `status: generated` in each delivered brief and in the queue table of `ai/README.md`.
2. Update `ai/generated/README.md`: one row per delivered file — ID, file, size in px and KB,
   background, and review notes (e.g. "regenerated twice: removed letter-like marks on the board").
3. Commit, push, and open the pull request into `main`:
   - title: `feat(ai): <batch> (<first ID>–<last ID>)`;
   - body: the delivery table, the ticked acceptance checks per brief, the checker output, and
     "Ready for Claude to review and install." No AI attribution.
4. Do not merge. If Claude or the user asks for changes, push new files to the same branch.

## 9. When in doubt

Choose the calmer, simpler, more respectful option, and say what you chose in the pull request. Never
add scenes, people or objects that a brief does not ask for. Never put text into an asset: every word the
user reads is real HTML text in the app, written in Indonesian by Claude.
